# ADR-0045: 다중일 검색 — 키워드 90일 + 기사 7일, 별도 JSON 인덱스, 최신성 가중

- Status: Accepted
- Date: 2026-10-20
- Deciders: yusik
- Related: [ADR-0002](./0002-frontend-nextjs-static-export.md), [ADR-0007](./0007-content-policy-headline-curation.md), [ADR-0042](./0042-site-search.md), [ADR-0044](./0044-keyword-page-persistence.md)

## Context (배경)

ADR-0042 의 사이트 검색은 **최신 스냅샷 하루치만** 인덱싱했다(키워드 40 + 기사 96, 인덱스 25KB). 당시엔 /k 페이지도 최신 키워드만 있었으므로 정합했고, "다일 검색은 후속"으로 남겼다.

ADR-0044 로 /k 페이지가 **90일 보존 창(1,876개)** 으로 살아나면서 정합이 깨졌다. 페이지는 있는데 검색으로는 못 찾는다 — 예: `/k/여행/`(마지막 등장 8월 10일)은 200 이지만 `/search?q=여행` 에선 키워드가 안 나온다. 사이트 안에서 과거 키워드 페이지로 가는 길이 사실상 외부 검색엔진뿐이었다.

범위별 인덱스 크기를 실측했다 (2026-10-19, 스냅샷 90일 창이 꽉 찬 상태):

| 범위 | 키워드 | 기사 | raw | gzip |
|---|---:|---:|---:|---:|
| 현행 (최신 하루) | 40 | 96 | 25KB | 8KB |
| 키워드 90일 + 기사 최신 | 1,876 | 96 | 194KB | 46KB |
| 키워드 90일 + 기사 7일 | 1,876 | 566 | 294KB | 77KB |
| 키워드 90일 + 기사 30일 | 1,876 | 2,267 | 661KB | 191KB |
| 키워드·기사 90일 | 1,876 | 6,857 | 1.6MB | 495KB |

전달 방식도 다시 봐야 했다. 인덱스는 `/search` 의 client component prop 으로 임베드돼 RSC 페이로드에 이스케이프된 문자열로 실리므로, HTML 에서는 인덱스 크기의 **약 2배**가 된다(현행 25KB 인덱스로도 `/search` HTML 99KB).

→ 운영자 결정(2026-10-20, AskUserQuestion): **키워드 90일 + 기사 7일 / 별도 JSON 파일 + fetch / 날짜 표기 + 최신성 가중.**

## Decision (결정)

### 1. 검색 범위 = 키워드 90일 + 기사 7일

- **키워드** — 키워드 인덱스(`listKeywordEntries()`, ADR-0044)를 그대로 쓴다. 검색 결과의 키워드 집합 = 살아있는 /k 페이지 집합이 **구성상 일치**하므로 검색 결과가 404 로 가지 않는다. 소문자 기준 병합·최근 표기 유지도 키워드 인덱스가 이미 처리.
- **기사** — 최근 `SEARCH_ARTICLE_DAYS = 7` 일 스냅샷. id 기준 중복 제거, 며칠 연속 수집된 기사는 가장 최근 수집일을 남긴다. 기사 제목·URL·매체명만 인덱싱(ADR-0007 — 본문 미저장 원칙 유지).
- `KeywordEntry` 에 마지막 등장일의 `traffic` 을 추가 — /k 페이지가 `findTrendByKeyword` 로 집는 항목과 같은 트렌드의 값.

### 2. 인덱스 전달 = 별도 JSON 파일 + fetch

- `src/app/search-index.json/route.ts`(`force-static`) 가 빌드타임에 `out/search-index.json` 을 생성. 형태 `{ date, docs }` — `date` 는 최신 스냅샷 일자('오늘'의 기준).
- `/search` 는 `/search-index.json?v=<최신일자>` 를 `SearchClient` 에 넘기고, 같은 URL 을 `preload(as: 'fetch')` 해 하이드레이션 전에 다운로드를 시작한다(`?q=` 랜딩 지연 단축). 파일은 `_headers` 로 1일 캐시 — URL 이 매일 바뀌므로 안전.
- 로딩 중·실패 상태 문구를 둔다. 빈 입력 화면(검색 UI·안내문)은 그대로 정적 HTML 에 포함.

### 3. 과거 결과 표시 = 날짜 표기 + 최신성 가중

- 결과 행마다 날짜 — 키워드는 마지막 등장일, 기사는 수집일. 인덱스 기준일이면 `오늘`(강조), 아니면 `M월 D일`(90일 창이라 연도 생략).
- 점수에 최신성 가산 `round(6 / (1 + 경과일/7))` — 오늘 6, 1주 전 3, 한 달 전 1, 그 뒤 0. 매칭 단계 간격(exact 100 · prefix 60 · includes 40)보다 작아 **비슷한 점수끼리만** 순서를 바꾼다. 동점 정렬에 최근 일자 우선 추가.
- 그룹 구조(키워드 / 카테고리 / 뉴스)는 유지.

## Consequences (결과)

**긍정**

- 과거 키워드 페이지 1,876개가 사이트 검색으로 도달 가능 — 내부 링크 경로가 생긴다.
- `/search` HTML 99KB → 67KB (gzip 19.4KB → 11.3KB). 인덱스는 HTML 과 분리돼 따로 캐시된다.
- 실측(헤드리스 Chromium, 390px): 페이지당 인덱스 요청 1회(preload 재사용, 중복 다운로드 없음), 콘솔 경고 0, 가로 스크롤 없음. `q=여행` → 키워드 `여행 · 2000+ · 8월 10일` 노출.
- 단위 테스트 78 → 84 — 다일 병합·최신 수집일 유지·최신성 가산·단계 역전 금지·날짜 라벨·traffic 기록.

**부정 / 트레이드오프**

- 검색 시 인덱스 **376KB raw / 81.5KB gzip** 다운로드(현행 8KB gz 대비 10배). `/search` 방문 시에만 발생하고 홈·타 페이지엔 영향 없음. 모바일 실기기에서의 파싱 시간은 측정하지 않았다.
- 요청이 1개 늘고, `?q=` 랜딩에선 인덱스 도착 전까지 "불러오는 중" 이 잠깐 보인다(preload 로 최소화).
- 최신성 가중은 관련도와 별개 신호라, 비슷한 점수에선 덜 관련된 최근 결과가 위로 올 수 있다(예: `갤럭시` → `la 갤럭시`(10월) 가 `삼성 갤럭시`(9월) 보다 위).
- 7일보다 오래된 기사는 검색되지 않는다 — 해당 키워드의 /k 페이지(마지막 등장일 기사 포함)로는 여전히 도달 가능.

**중립**

- 산출물 파일 수 5,980 → 5,982. 90일 창이 다 차서 키워드·/d 페이지 수는 정상상태(키워드 약 1,900)에 머문다 — Cloudflare 무료 한도 20,000 의 30%.
- 키워드 URL(퍼센트 인코딩)이 인덱스 raw 크기의 상당 부분을 차지한다. 커지면 title 에서 클라이언트가 URL 을 재구성하는 방식으로 줄일 수 있다.

## Alternatives Considered (대안)

- **키워드 90일 + 기사 최신만** (46KB gz) — 가장 가볍지만 기사 검색 적중률이 현행과 같다.
- **키워드 90일 + 기사 30일** (191KB gz) / **전부 90일** (495KB gz) — 기사 커버리지는 넓지만 클라이언트 검색으로는 무겁고, 오래된 기사는 링크가 깨지기 쉽다.
- **HTML 임베드 유지** — 요청이 늘지 않지만 `/search` HTML 이 인덱스의 약 2배(7일 범위 약 600KB raw)로 커진다.
- **날짜 표기만 (순위 불변)** — 오래된 키워드가 오늘 키워드보다 위에 올 수 있다.
- **오늘 / 지난 결과 그룹 분리** — 구분은 명확하지만 그룹이 늘어 결과 화면이 길어진다.
